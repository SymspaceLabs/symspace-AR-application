# Human-in-the-loop review and annotation tooling for AI-generated AR product GLBs (as of 2026-10-07)

Scope note: this covers (a) open-source building blocks for a lightweight "AR asset configurator" review UI, (b) commercial 3D asset review / QC / AR-config platforms, (c) outsourced human services and per-asset costs, (d) workflow design so each manual correction becomes gold-set / training data, and (e) attachment-node naming conventions inside the GLB. Several primary vendor/doc domains (gltf-transform.dev, modelviewer.dev, khronos.org, docs.blender.org, developers.snap.com, modelry.ai, zakeke.com, costbench.com, aboutwayfair.com, docs.supervisely.com) were blocked by the research proxy; where I fell back to GitHub mirrors, search snippets or third-party aggregators this is marked explicitly. Prices from aggregator sites (Capterra, GetApp, SoftwareSuggest, Costbench, fibbl) are "independent/aggregator-reported", not vendor-verified, unless the vendor page itself was reached.

## KQ1. Open-source building blocks for a browser-based "click a vertex, type dimensions, pick category, export JSON" tool, and existing open projects close to it

### Takeaway
No existing open project does exactly "pick wearable attachment points on a product GLB + set scale/pivot/front axis + export sidecar JSON"; the fastest path is a small custom web page built on three.js (`GLTFLoader` + `TransformControls` + raycast picking) or on `<model-viewer>` (its hotspot/annotation API already stores clicked surface position + normal), with glTF-Transform (MIT, Node API) doing the programmatic write-back (`center`, node transforms, `extras`, XMP). Keypoint-annotation precedents worth borrowing from are KeypointNet (stores keypoints as face index + barycentric uv + xyz), MeshLab PickPoints (`.pp` files) and 3D-BAT; CVAT is cuboid-only for 3D and Label Studio has no documented mesh support.

### Cited Findings

**three.js / editor / gizmos**
- The three.js editor (threejs.org/editor) could not be fetched directly in this session (GitHub README path returned 404); its feature set is known from community tooling built on it. A representative three.js-based level editor ("Three.js Level Creator") advertises "Transform Gizmos for move, rotate and scale with snapping", glTF import and export of a simple JSON file — the same primitives a configurator needs — [itch.io devlog](https://defacci.itch.io/threejs-level-creator/devlog/1458096/threejs-level-creator-first-release)
- Needle Engine's `TransformGizmo` "wraps three.js TransformControls with keyboard shortcuts and snapping support", confirming `TransformControls` is the standard gizmo building block — [Needle Engine API docs](https://engine.needle.tools/docs/api/TransformGizmo)
- In the three.js editor, `userData` edited by in-editor scripts "don't reflect to the actual editor and are overwritten", i.e. the editor's scripting hook is not a reliable way to author per-node metadata; a custom page is cleaner — [three.js discourse](https://discourse.threejs.org/t/how-can-i-set-an-objects-userdata-using-a-script-in-the-editor/76935)
- `@gltf-transform/view` "creates three.js objects from a glTF Transform Document and keeps the three.js scene graph updated in realtime as changes are made, providing a lossless workflow to load, view, edit, and export glTF assets", and the author contrasts it with `THREE.GLTFExporter`, which "is lossy and expensive" — [npm @gltf-transform/view](https://npmjs.com/package/@gltf-transform/view); [socket.dev listing](https://socket.dev/npm/package/@gltf-transform/view/overview/0.4.6)

**glTF-Transform (MIT)**
- CLI command list (read from the CLI source `packages/cli/src/cli.ts`): `inspect`, `validate`, `copy`, `optimize`, `merge`, `partition`, `dedup`, `prune`, `gzip`, `xmp` ("Add or modify XMP metadata"), `center` ("Center the scene at the origin, or above/below it"), `instance`, `flatten`, `join`, `draco`, `meshopt`, `quantize`, `dequantize`, `weld`, `unweld`, `tangents`, `unwrap`, `reorder`, `simplify`, `metalrough`, `palette`, `unlit`, `resize`, `etc1s`, `uastc`, `ktxdecompress`, `ktxfix`, `avif`, `webp`, `png`, `jpeg`, `resample`, `sequence`, `sparse`. **No `scale`, `rotate` or general `transform` CLI command exists** — [glTF-Transform cli.ts (GitHub raw)](https://raw.githubusercontent.com/donmccurdy/glTF-Transform/main/packages/cli/src/cli.ts)
- CLI README: "Copyright 2023, MIT License"; `optimize` runs the common optimizations in one step; documentation lives at gltf-transform.dev/cli (blocked here) — [glTF-Transform CLI README](https://raw.githubusercontent.com/donmccurdy/glTF-Transform/main/packages/cli/README.md); [CLI quickstart page (blocked, listed for the writer)](https://gltf-transform.dev/cli)
- glTF-Transform ships a `KHRXMP` extension class for `KHR_xmp_json_ld` — [gltf-transform KHRXMP docs](https://gltf-transform.donmccurdy.com/modules/extensions/classes/KHRXMP)
- The glTF `extras` field "is a catch-all container for custom JSON metadata that can be attached to any object in the glTF hierarchy—nodes, meshes, materials, and even animations" — [Vulkan tutorial: Metadata & Physics Extras](https://docs.vulkan.org/tutorial/latest/Advanced_glTF/Scene_Graph_Hierarchy/04_metadata_and_physics_extras.html)

**Google `<model-viewer>` editor**
- The model-viewer editor (modelviewer.dev/editor; source package `space-opera` — direct fetch blocked/404) "allows users to load a GLB/GLTF model, add hotspots to it, and create code snippets"; it supports "adding hotspots to loaded models, editing hotspot size/color and annotations, and deleting hotspots"; in `<model-viewer>`, child elements are hotspots "if their slot begins with 'hotspot', with the `data-position` attribute specifying the 3D position and `data-normal` attribute specifying the normal vector" — [model-viewer annotations example](https://modelviewer.dev/examples/annotations/); [dave-kramer/modelviewer (community editor fork)](https://github.com/dave-kramer/modelviewer)
- `<model-viewer>` supports export "as GLB with options for binary format, visibility filtering, image embedding, and texture resolution control" via its scene-graph API — [model-viewer scene-graph docs mirror](https://tessl.io/registry/tessl/npm-google--model-viewer/files/docs/scene-graph.md)

**Blender as reviewer tool (bpy addon + glTF exporter extras)**
- glTF-Blender-IO docs (Blender 4.4): "Custom properties are always imported, and will be exported from most objects if the Include → Custom Properties option is selected before export"; "Custom Properties of the collection are exported as Scene glTF extras"; export uses "+Y up" glTF convention; "Apply Modifiers" exports the evaluated mesh — [glTF-Blender-IO docs (GitHub)](https://github.com/KhronosGroup/glTF-Blender-IO/blob/main/docs/blender_docs/scene_gltf2.rst); [older user.md](https://github.com/KhronosGroup/glTF-Blender-IO/blob/5091d98b800e36dde25581aa9523d2ba7cbce0b2/docs/user.md)
- Workflow confirmed by third-party tutorial: select object → Object Properties → Custom Properties → export with Include → Custom Properties; "Blender will serialize those properties into the extras field of the corresponding node" — [Vulkan tutorial](https://docs.vulkan.org/tutorial/latest/Advanced_glTF/Scene_Graph_Hierarchy/04_metadata_and_physics_extras.html)
- three.js `GLTFLoader` maps glTF `extras` to `object.userData` (issue thread on exporting custom attributes/extras) — [three.js issue #18445](https://github.com/mrdoob/three.js/issues/18445); [three.js discourse: GLTF export custom attributes](https://discourse.threejs.org/t/gltf-export-custom-attributes/12443)

**Unity side (reading names/extras at runtime)**
- UnityGLTF README: recommended "Long-Term Support versions of Unity (2021.3+, 2022.3+, 6000.0+)"; runtime loading via `GLTFComponent` or `GLTFSceneImporter` (local `UnityWebRequestLoader` or remote URL; result in `import.LastLoadedScene`); extensibility via `GLTFImportPlugin` / `GLTFExportPlugin` registered under Project Settings > UnityGLTF; custom extension data via `GLTF.Schema.IExtension`. The README "does not explicitly address whether node names are preserved as GameObject names" — [UnityGLTF README (GitHub raw)](https://raw.githubusercontent.com/KhronosGroup/UnityGLTF/dev/README.md)
- glTFast (alternative loader) documents an Add-on API that imports "custom data from the extras property of a glTF node" using Newtonsoft JSON, requiring `com.unity.cloud.gltfast` + `com.unity.nuget.newtonsoft-json` — [glTFast "Use case: custom extras" (6.9)](https://docs.unity3d.com/Packages/com.unity.cloud.gltfast@6.9/manual/UseCaseCustomExtras.html)

**Existing 3D keypoint / mesh annotation projects**
- KeypointNet (CVPR 2020): "a web annotation tool based on NodeJS that allows users to click up to 20 interest points" on meshes; the released dataset stores each keypoint as `point_index` (on a 2,048-point sampled cloud), `face_index` + `face_uv` (barycentric on the mesh), and `xyz`; repo is MIT — [KeypointNet paper (arXiv)](https://arxiv.org/pdf/2002.12687); [KeypointNet repo](https://github.com/qq456cvb/KeypointNet)
- MeshLab's point-picking tool writes `.pp` "picked point" files; a Python package `meshlab-pickedpoints` reads/writes them and R's `Morpho::read.mpp` imports them — [PyPI meshlab-pickedpoints](https://pypi.org/project/meshlab-pickedpoints/1.0.0b0); [Morpho read.mpp](https://search.r-project.org/CRAN/refmans/Morpho/html/read.mpp.html)
- MeshEditor (PyPI) "enables vertex selection, deletion and basic landmarking of a 3D mesh, and allows saving the resulting mesh or landmark coordinates" — [PyPI mesheditor](https://pypi.org/project/mesheditor)
- StrayRobots 3d-annotation-tool: GUI "for annotating point clouds and Stray scenes that supports keypoints among other label types" — [GitHub StrayRobots/3d-annotation-tool](https://github.com/StrayRobots/3d-annotation-tool)
- SAM-3D-Selector: converts 2D SAM masks to 3D mesh/point-cloud selections; "keypoint annotation available by clicking with the left mouse button" — [GitHub nexuslrf/SAM-3D-Selector](https://github.com/nexuslrf/SAM-3D-Selector)
- 3D-BAT: "open source, web-based" 3D bounding-box toolbox for autonomous-driving data (multi-view Masterview, interpolation, AI-assisted labeling, active-learning support, OpenLABEL) — bounding boxes, not surface keypoints — [arXiv 1905.00525](https://arxiv.org/pdf/1905.00525); [3d-bat releases mirror](https://git.tdem.in/walzimmer/3d-bat/releases)
- Scalabel: "versatile and scalable annotation platform supporting both 2D and 3D data labeling", used for BDD100K (driving data) — [PyPI scalabel](https://pypi.org/project/scalabel/)
- CVAT: "Annotation of point cloud data in CVAT is done exclusively with cuboids" — [CVAT blog: 3D point cloud annotation](https://www.cvat.ai/resources/blog/3d-point-cloud-annotation); [CVAT formats docs](https://docs.cvat.ai/v2.5.2/docs/getting_started/product_tour)
- Supervisely has a browser mesh-labeling toolbox "for 3D surface data with features such as vertex painting with an adjustable brush" (docs page blocked; from search snippet) — [Supervisely mesh labeling docs](https://docs.supervisely.com/labeling/labeling-toolbox/meshes)
- labelCloud: point-cloud bounding-box tool (not keypoints) — [labelCloud publication record](https://fis.tu-dresden.de/portal/en/publications/labelcloud(3a14f389-016b-4686-8a40-184518a996c2).html)

### Inferences
- Fastest build: a single-page three.js app (GLTFLoader + OrbitControls + TransformControls + `Raycaster` for vertex/face picking) with a right-hand form (category dropdown, dimension fields, front-axis radio, attachment-point list). On "Approve", POST a sidecar JSON; optionally run glTF-Transform's Node API server-side to (1) `center()` the asset per the chosen pivot rule, (2) add empty child `Node`s named per the anchor convention with `setTranslation/setRotation` and `setExtras({...})`, (3) write a `KHR_xmp_json_ld` packet. `@gltf-transform/view` is the right bridge if the tool must edit the glTF Document directly and preview losslessly, avoiding `THREE.GLTFExporter` round-trips.
- `<model-viewer>` editor is the quickest *prototype*: its hotspot workflow already yields `data-position` + `data-normal` on click, which is exactly an attachment point + surface normal; but it lacks numeric dimension entry, pivot/front-axis controls, and export of a Unity-oriented JSON, so it is a 1–2 day prototype rather than the end state.
- Babylon Sandbox and the three.js editor are good for *inspection* but poor for *authoring metadata* (lossy GLB re-export; `userData` edits unreliable), so use them as viewers only.
- Blender route (bpy addon with "Set origin to bottom-centre", "Apply real height = X mm", "Add anchor empty at 3D cursor", one-click export with Custom Properties) is the strongest option if reviewers are 3D-literate; empties export as glTF nodes and their custom properties land in `extras`. Its downside is desktop install + Blender UX for non-artists.
- Store picked points as KeypointNet does (face index + barycentric uv + xyz) rather than raw vertex index, because TRELLIS/Pixal re-meshing or decimation (glTF-Transform `simplify`/`weld`) changes vertex indices but a barycentric point on a face can be re-projected onto a new mesh by nearest-surface-point.
- Dedicated 3D annotation suites (CVAT, 3D-BAT, Scalabel, labelCloud) are tuned for LiDAR cuboids and would need forking to add mesh surface keypoints; not worth adopting for this use case.

### Gaps
- Could not fetch threejs.org/editor source README, gltf-transform.dev/cli page, modelviewer.dev/editor page, docs.blender.org, or Supervisely docs (egress blocked); feature claims above rely on GitHub source, mirrors and snippets.
- glTF-Transform's *Node API* methods for node transforms (`setTranslation/setRotation/setScale`, `setExtras`) were not verified in this session (only the CLI command list was); the writer should treat "programmatic node transforms via Node API" as highly likely but unverified.
- Label Studio: no documented mesh/point-cloud labeling found in search; treat as "no official 3D mesh support" (unverified absence).
- No open project found that combines wearable attachment-point picking with AR scale/pivot authoring; "Annotate3D" and "Blender keypoint annotation addon" searches returned nothing specific.

Commercial platforms split into (a) 3D DAM/optimization/QA (VNTANA, Echo3D, Sketchfab, Modelry/Arsenal) that handle approval workflows and glTF/USDZ output but do not expose wearable anchor authoring, (b) configurator/visualization platforms (Threekit, Zakeke, Dopple/Emersya, Threedium) priced from ~$20/mo (Zakeke) to $50–150k+/yr (Threekit), and (c) Dopple, which uniquely documents a built-in glTF editor with an "edit mode". ### Inferences
- For Symspace's volume (tens-to-hundreds/month) and need for *wearable anchors*, no commercial platform removes the need for a custom config step: they standardize floor-placed products (bottom-centre pivot, metric scale) but not ring/watch/glasses frames. ## KQ4. Workflow design for a data flywheel: storing corrections, auto-applying by nearest neighbour, gold set, measuring automation accuracy

### Takeaway
Standard HITL/MLOps pattern applies directly: run the automatic configurator, compute a confidence score, auto-approve above threshold, route the rest to the review UI, and ingest every reviewer action as a labelled example; corrections should be stored in mesh-invariant form (barycentric face points, metric dimensions, category, per-category pivot/front rules) so they can be re-projected onto re-generated meshes and used as both nearest-neighbour priors and evaluation gold set. Public e-commerce 3D pipeline write-ups (Wayfair, Amazon, Khronos BoF) confirm QA is 15–20% of asset effort and that ML is used to assist modelling, but none publishes an anchor-level correction schema.

### Cited Findings
- HITL definition: "people stay actively involved in an automated or machine learning process, reviewing, correcting, or approving the model's outputs rather than letting it run fully autonomously" — [Voxel51 glossary](https://voxel51.com/glossary/human-in-the-loop)
- Fallback-with-active-learning pattern (patent): "a hard rule fallback process is performed when the deployed model falls below a confidence threshold, but before human intervention is required" — [USPTO 11663409](https://image-ppubs.uspto.gov/dirsearch-public/print/downloadPdf/11663409)
- Active learning: "the model identifies the data points it's least confident about and routes them to a human expert for labeling… retrain on the exact cases where the model struggles most" — [Roboflow: HITL for high-stakes AI](https://blog.roboflow.com/human-in-the-loop-ai/)
- "The canonical HITL flow runs in six stages: data collection, model inference, confidence scoring, routing logic, human review, and feedback ingestion" — [TrustLayer: HITL practical framework](https://trustlayer.io/resources/human-in-the-loop-a-practical-automation-framework)
- "Human-in-the-loop pipeline (Active learning strategy and human annotation) can improve productionized models iteratively by adopting this strategy in an MLOps lifecycle" — [Fifth Elephant MLOps Conference talk](https://hasgeek.com/fifthelephant/mlops-conference/sub/building-human-in-the-loop-pipeline-in-mlops-7dwbhBAGSDCjDCyR4wwSvp); a Conf42 MLOps 2025 talk claims HITL patterns "can boost model performance by 40%" (speaker claim, unverified) — [Conf42 MLOps 2025](https://www.conf42.com/MLOps_2025_Tejasvi_Nuthalapati_human_loop_mlops)
- KeypointNet stores each human keypoint as `face_index` + `face_uv` (barycentric) + `xyz` + `point_index`, enabling re-projection across mesh/point-cloud representations — [KeypointNet repo](https://github.com/qq456cvb/KeypointNet)
- Wayfair: "developed a 3D content pipeline to create app-ready real-scale 3D models" for WayfairView AR; "Producing 3D models quickly and accurately is key… Wayfair utilizes machine learning to aid 3D modeling"; audits include "practical audits where employees physically check samples to verify model results" (blog blocked; from search snippets) — [Wayfair Tech Blog: 3D Model API](https://www.aboutwayfair.com/tech-innovation/wayfairs-3d-model-api); [Wayfair tech blog listing](https://www.aboutwayfair.com/careers/tech-blog?p=14)
- Khronos BoF with retailers: "15-20% of effort in asset creation going to quality assurance, and over 30 major parameters for quality assurance of an asset" — [Khronos BoF](https://www.khronos.org/developers/linkto/how-do-we-solve-the-challenges-of-gltf-asset-creation-bof)
- Amazon: "the scalability of 3D content to span the entire catalog is multiple orders of magnitude beyond what current technologies and approaches can achieve, so Amazon is taking a science-first automation approach"; emphasis on "Reusable labeling pipelines, evaluation frameworks, and inference infrastructure" (job postings) — [Amazon jobs: Visual Innovation Sciences](https://amazon.jobs/en/jobs/2401023/postdoctoral-scientist-visual-innovation-sciences); ABO dataset: ">7,900 products… high-quality 3D models with 4K texture maps" usable as a scale/orientation reference set — [ABO dataset summary (V7)](https://www.v7labs.com/open-datasets/amazon-berkeley-objects-abo-dataset)
- Articraft (2026) frames asset creation as "an edit–execute–repair loop grounded in validation and geometric feedback, without relying on rendered visual inspection" and released 10K assets with "semantic part structures, joint specifications, and generation traces" — [arXiv 2605.15187](https://arxiv.org/abs/2605.15187)
- AssetGen (2026) ran "a blind human evaluation on 195 image-conditioned assets… evaluated the asset itself under direct inspection" — [arXiv 2605.26137](https://arxiv.org/pdf/2605.26137); Seed3D 1.0 used "14 human evaluators… 43 diverse test images" across geometry/texture dimensions — [arXiv 2510.19944](https://arxiv.org/pdf/2510.19944)
- Toloka's quality controls (gold questions, overlap, majority vote) are the standard crowd-side mechanisms for measuring annotator accuracy — [Toloka docs: save money](https://toloka.ai/docs/guide/save-money/)

### Inferences
- Correction record schema (per asset, append-only events): `{asset_id, product_id, category, source_model (TRELLIS.2/Pixal3D + version), input_image_hash, image_embedding, mesh_embedding, auto_config_v, reviewer_id, action: approve|edit|reject, fields_changed: {scale_m, pivot_rule, front_axis, category, anchors:[{name, face_index, bary_uv, xyz, normal, axis_quat}]}, reject_reason, time_spent_s}`. Keep the *auto-proposed* values alongside the *final* values so the delta is the training signal.
- Nearest-neighbour auto-apply: on a new asset, embed the product image (and optionally a mesh descriptor), retrieve k approved records of the same category/product family, and seed the configurator with their per-category pivot rule, front axis and dimension prior; for anchors, transfer the barycentric point via nearest-surface-point on the new mesh (valid because KeypointNet-style storage is mesh-index-independent).
- Gold set: every reviewer-approved config becomes an evaluation case; measure automation as (a) auto-approve rate at threshold, (b) field-level agreement (scale within ±5%, front axis exact, anchor position error in mm/normal angle), (c) reviewer edit time. Re-run the automated configurator against the gold set on each model/prompt change; this is the "evaluation framework" piece Amazon's postings describe.
- Routing: start with 100% human review; once per-category agreement exceeds a target (e.g. 95% on scale/front axis), flip that category to auto-approve with random audit sampling (the "physical sample audit" idea from Wayfair, applied virtually), keeping anchors on human review longest because they carry the highest AR-visible error cost.

### Gaps
- No public engineering blog from IKEA, Shopify, Zalando or Myntra describing anchor-level or correction-level 3D QA schemas was found in this session; Wayfair's blog pages were blocked (only snippets).
- No peer-reviewed paper specifically on "human-in-the-loop 3D asset QA for AR commerce" was found; the closest are the 2026 generation papers' human-evaluation protocols.
- The "40% boost" HITL claim is a conference-talk assertion, not a measured result from a comparable pipeline.

## KQ5. Naming conventions for attachment nodes inside the GLB so Unity finds them by name; precedents

### Takeaway
There is no Khronos standard for wearable anchors; precedents are (1) Snap Lens Studio's fixed attach-point vocabulary (Head Center, Candide Center, Left/Right Eyeball), (2) Mixamo's `mixamorig:` prefixed bone names and VRM's explicit index-mapped `humanBones` extension, and (3) Khronos 3D Commerce's XMP `model3d` namespace for asset-level AR orientation metadata. A pragmatic standard is a prefixed, lower-snake-case node name (`anchor_<kind>_<detail>`) matching the 3D Commerce file-naming character set, with optional `extras` for axis/role, which both UnityGLTF (`GameObject.Find`/transform search) and three.js can locate without extension parsing.

### Cited Findings
- Snap Lens Studio: 3D objects attach to a face via a "Head Binding" object; "You can modify which part of the face the Head Binding is attached to by changing the Attach to Point"; on Spectacles/Camera Kit "only Left Eyeball, Right Eyeball, Candide Center, Head Center attachment points are supported"; Head Binding includes a Face Occluder child (docs blocked; from snippets) — [Snap docs: Head Attached 3D Objects](https://developers.snap.com/lens-studio/features/ar-tracking/face/head-attached-3d-objects)
- Mixamo: "The 'Mixamorig:[name]' format has been used since the beginning of Mixamo"; Hips is the topmost bone; retargeting tools default to stripping prefixes like `mixamorig:` and `Armature|` — [Adobe community (Mixamo)](https://community.adobe.com/t5/mixamo-discussions/pre-rigged-blender-character-quot-unable-to-map-your-existing-skeleton-quot/m-p/12196889); [three.js discourse on SkeletonUtils retarget](https://discourse.threejs.org/t/fixing-skeletonutils-retarget-and-retargetclip-functions/65149/7)
- VRM 1.0: humanoid bones are mapped via extension JSON `"humanBones": { "boneName": { "node": nodeIndex } }`, not by node name; "humanoid bones must be unique in VRM"; names like `hips, spine, chest, head, leftEye, rightEye, leftUpperArm…` — [VRMC_vrm-1.0 humanoid spec](https://github.com/vrm-c/vrm-specification/blob/master/specification/VRMC_vrm-1.0/humanoid.md)
- KHR_xmp_json_ld: packets can attach to Asset, Scene, Node, Mesh, Material, Image, Animation; objects reference packets via `"extensions": { "KHR_xmp_json_ld": { "packet": 0 } }`; the spec README itself contains no `model3d`/AR-orientation mention — [KHR_xmp_json_ld README](https://github.com/KhronosGroup/glTF/blob/main/extensions/2.0/Khronos/KHR_xmp_json_ld/README.md)
- Khronos 3D Commerce metadata: "The model3d namespace provides certain properties specific to 3D content, such as Augmented Reality (AR) orientation data"; namespace URI `https://schema.khronos.org/model3d/xsd/1.0/`; "Generally XMP metadata is associated with the entire glTF asset… in less common cases XMP Packets may be attached to Scene, Node, Mesh…" (blog blocked; from snippets + glTF-Transform docs) — [Khronos blog: pervasive asset metadata in 3D Commerce](https://www.khronos.org/blog/pervasive-asset-metadata-in-3dcommerce); [glTF-Transform KHRXMP docs](https://gltf-transform.dev/modules/extensions/classes/KHRXMP)
- Khronos 3D Commerce asset guidelines v2.0.0 naming charset: "a-z, _, -, 0–9… start the file name with a letter… Use underscore _ or hyphen - to separate words" — [3DC-Asset-Creation guidelines](https://github.com/KhronosGroup/3DC-Asset-Creation/blob/main/asset-creation-guidelines/RealtimeAssetCreationGuidelines.md)
- UnityGLTF loads scenes into a GameObject hierarchy (`import.LastLoadedScene`) and supports custom extension deserialization via `GLTF.Schema.IExtension` / import plugins; the README does not state node-name preservation explicitly — [UnityGLTF README](https://raw.githubusercontent.com/KhronosGroup/UnityGLTF/dev/README.md)
- Blender exports object custom properties to node `extras`; empties become nodes (Blender docs blocked; from glTF-Blender-IO docs and tutorial) — [glTF-Blender-IO docs](https://github.com/KhronosGroup/glTF-Blender-IO/blob/main/docs/blender_docs/scene_gltf2.rst); [Vulkan tutorial on extras](https://docs.vulkan.org/tutorial/latest/Advanced_glTF/Scene_Graph_Hierarchy/04_metadata_and_physics_extras.html)
- three.js `GLTFLoader` exposes glTF node `extras` as `object.userData` (discussion context) — [three.js issue #18445](https://github.com/mrdoob/three.js/issues/18445)

### Inferences
- Proposed convention (not a published standard): reserved prefix `anchor_`, lower snake_case, 3D-Commerce charset, one node per attachment frame, child of the root product node, identity scale, with +Y of the node = the functional axis and +Z = "outward/front" of the frame. Suggested vocabulary: `anchor_ring_axis` (node origin on finger axis at ring centre, +Y along finger), `anchor_watch_band` (origin on wrist centreline under case, +Y along forearm), `anchor_glasses_bridge` (origin at bridge midpoint, −Z towards face), `anchor_earring_hook` (origin at hook top, +Y up), `anchor_shoe_sole` / `anchor_shoe_heel` (origin at heel contact point, +Z toe direction), plus `anchor_floor` / `anchor_wall` / `anchor_table` for placement categories. Add `extras: {"symspace_anchor": {"kind": "ring_axis", "version": 1, "source": "human|auto", "confidence": 0.0-1.0}}` for tooling that can read extras, but keep the name authoritative so UnityGLTF needs no plugin.
- Mirroring Snap's "fixed vocabulary" and VRM's "unique per asset" rules avoids ambiguity: one anchor of each kind per GLB, validated in the review tool and in a CI `gltf-transform inspect`-style check.
- Store asset-level data (category, real dimensions, front axis, pivot rule) in a root `KHR_xmp_json_ld` packet using the 3D Commerce `model3d` namespace where fields exist, and in the sidecar JSON for the Unity runtime; the sidecar remains the source of truth because UnityGLTF's XMP support was not verified.

- The exact property names in Khronos' `model3d` XMP namespace (e.g., for AR orientation/dimensions) could not be retrieved (khronos.org blocked); the writer should cite the namespace URI only.
- No source confirms that UnityGLTF preserves glTF node names as GameObject names (widely assumed; unverified here) or that it parses `KHR_xmp_json_ld`.
