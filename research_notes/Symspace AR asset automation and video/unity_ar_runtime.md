## Key Question 1 — AR Foundation 6.x feature matrix per provider, XR Hands, 2025–2026 platform changes, Unity MARS status

### Takeaway
AR Foundation (now at 6.6.0 release / 6.7.0-pre.1) still gives you planes, faces, occlusion, anchors, image tracking and light/env probes on both ARCore and ARKit, but body tracking remains ARKit-only, hand tracking is not exposed at all on handheld iOS/Android (XR Hands is OpenXR/headset-only), meshing is ARKit-only among phones, and Unity MARS is deprecated as of Unity 6.1 and should be removed. Nothing in 2025–2026 added hand or body tracking to ARCore on phones, and ARKit body tracking has an open, unacknowledged regression on iOS 26.x.

**ARKit provider specifics:**
- ARKit face tracking requires "Apple Neural Engine with iOS 14+ or iPadOS 14+" or a TrueDepth camera on iOS 13 or earlier; it uses the "selfie" (user-facing) camera; simultaneous world-facing and user-facing cameras are possible via a custom configuration chooser (iOS 13+); optional features supported: face pose, mesh vertices/indices, UVs, eye tracking, blend shapes (normals not supported); blend shape weights range 0.0–1.0 via `ARKitBlendShapeLocation`. — [arkit-face-tracking.md](https://raw.githubusercontent.com/needle-mirror/com.unity.xr.arkit/master/Documentation~/arkit-face-tracking.md)
- ARKit occlusion: human depth & stencil need iOS 13+ with A12 or newer; environment depth needs an iOS 14 device with LiDAR; smoothed depth must be requested via `environmentDepthTemporalSmoothingRequested = true`; raw/smoothed depth map to `ARFrame.sceneDepth` / `ARFrame.smoothedSceneDepth`. — [arkit-occlusion.md](https://raw.githubusercontent.com/needle-mirror/com.unity.xr.arkit/master/Documentation~/arkit-occlusion.md)
- Apple `ARFaceAnchor` (iOS 11+): "An anchor for a unique face that is visible in the front-facing camera"; "ARKit can track multiple faces simultaneously"; face coordinate space in meters with origin centered behind the face; exposes `geometry` (ARFaceGeometry), `blendShapes` dictionary, `leftEyeTransform`, `rightEyeTransform`, `lookAtPoint`. — [Apple ARFaceAnchor](https://developer.apple.com/documentation/arkit/arfaceanchor.md)
- The commonly cited ARKit numbers are 1,220 mesh vertices and 52 blend-shape coefficients; these numbers were **not verified from a fetched Apple page** in this session (the ARFaceGeometry page is JS-rendered). — [ARFaceGeometry page (content not retrievable)](https://developer.apple.com/documentation/arkit/arfacegeometry)
- Apple `ARBodyTrackingConfiguration` (iOS 13+): "tracks human body poses, planar surfaces, and images using the rear-facing camera"; plane detection and image detection can be enabled alongside it; `frameSemantics` includes `bodyDetection` by default giving 2D joints via `ARFrame.detectedBody`; `automaticSkeletonScaleEstimationEnabled` estimates body height; environment texturing is supported. — [Apple ARBodyTrackingConfiguration](https://developer.apple.com/documentation/arkit/arbodytrackingconfiguration.md)
- "Person segmentation with depth and body detection frame semantics are mutually exclusive" (`.bodyDetection` + `.personSegmentationWithDepth` returns unsupported); people occlusion requires A12+. — [Apple forum: Body tracking AND People Occlusion at same time?](https://developer.apple.com/forums/thread/124944) (search snippet)
- **iOS 26 regression:** "Since updating to iOS 26.0 (and confirmed on 26.1), ARBodyTrackingConfiguration no longer detects a valid ARBodyAnchor on devices with LiDAR (e.g., iPhone 15 Pro, iPhone 17 Pro Max)… all joints return nil"; reproduces in Apple's own "Capturing Body Motion in 3D" sample; Feedback FB15128723; posts Oct–Dec 2025; no documented Apple response or workaround in the thread. — [Apple Developer Forums thread 804899](https://developer.apple.com/forums/thread/804899)

### Inferences
- The project is already on AR Foundation 6.2.0; upgrading to 6.6.0 (the current release line for Unity 6.x) is low-risk and brings the `TryGetBlendShapes` API, persistent anchors on ARCore, and Vulkan validation; 6.7 is pre-release. Note that AR Foundation 6.4+ requires Xcode 26 for iOS builds.
- Since Unity MARS is deprecated with support only for Unity 6.1 and the project runs 6000.2.x, remove `com.unity.mars` and `mars-ar-foundation-providers` and rely on plain AR Foundation managers (ARPlaneManager/ARFaceManager/ARHumanBodyManager), which the project already uses directly.
- Face try-on (glasses/earrings/necklaces/hats) is feasible natively on both platforms, but only ARKit offers eye transforms and blend shapes; on ARCore you have pose + 468-vertex mesh + 3 region poses. Earrings/necklaces need ear/neck anchors derived from mesh vertex indices on both platforms (see Q4).
- Body tracking (garments) is ARKit-only natively and currently broken on iOS 26.x per developer reports; Android has nothing native. Hands and feet have no native AR Foundation path on either phone platform; a cross-platform ML path is required (Q2).

## Key Question 2 — Gap fillers for hand / feet / body tracking on both platforms

### Takeaway
The most maintained open path in 2026 is MediaPipe-family landmark models (Hand Landmarker 21 pts, Pose Landmarker 33 pts incl. heel/foot-index, Face Landmarker) run either through Unity's own inference package (com.unity.ai.inference, branded "Sentis" again since 2.4.0, with Unity-published ONNX ports of BlazePose/BlazeHand) or through homuler's MediaPipeUnityPlugin (MIT, iOS+Android GPU, but no release since Nov 2024). Niantic Lightship 3.x is being sunset (works through 2027-02-28) and never shipped body or finger tracking; commercial references (Snap Camera Kit, DeepAR, Banuba) all offer foot/hand/body but are closed.

### Inferences
- Recommended cross-platform open path: one `ILandmarkProvider` abstraction with two interchangeable backends: (a) Sentis 2.6 running Unity's ONNX BlazeHand/BlazePose (pure C#, no native build pain, GPUCompute on Metal/Vulkan), and (b) homuler MediaPipe plugin (better tracking stacks: palm detector + landmarker + world landmarks + handedness, GPU delegate), accepting its native-library maintenance risk (no release in ~23 months). Keep the existing iOS Vision hand plugin as a third backend for iOS fallback.
- Feet: use Pose Landmarker's ankle/heel/foot-index landmarks (3 points per foot give a foot plane and heading) plus environment-depth sampling (ARCore/ARKit) for metric depth; this is the same approach Snap/DeepAR expose as "foot tracking" and the only open route found. Expect ~20–30 ms per frame on a Pixel-6-class GPU for full pose, which forces 30 fps budgets rather than 60.
- Garments: ARKit body tracking is the best native quality on iOS but should be wrapped behind the same abstraction so BlazePose can replace it when `ARHumanBodyManager` yields no joints (iOS 26.x regression) and on Android.
- Remove Lightship from consideration (sunset, AR Foundation 6 incompatibilities, no hand/body).

### Gaps
- No on-device FPS numbers for Sentis-run BlazePose/BlazeHand on mid-range phones were found (Unity's model cards on Hugging Face were blocked and no community benchmarks surfaced).
- Pixel 6 CPU/GPU latency tables for Pose Landmarker and Face Landmarker tasks could not be fetched (ai.google.dev blocked); only legacy Pixel 3 numbers and Hand Landmarker 12.27 ms GPU were obtained.
- homuler plugin's compatibility with Unity 6.2/6.3 and 16 KB-page requirements on Android 15+ beyond v0.16.2 is unverified.
- Snap Camera Kit terms of use for commerce apps (brand/lens hosting requirements) not examined.

## Key Question 3 — Runtime GLB loading: UnityGLTF (Needle/Khronos) vs Unity glTFast; applying sidecar config

### Takeaway
Both libraries are production-grade in 2026; UnityGLTF (Khronos repo maintained by prefrontal cortex/Needle, 2.20.0, MIT) actually has the broader material/extension coverage (iridescence, sheen, KHR_animation_pointer, meshopt 0.2) and the project already uses it, while glTFast (6.20.0 / 7.0.0-exp.1, Apache-2.0, Unity ≥ 6000.0) has a cleaner Burst/Jobs import path and an official Add-on API for `extras`. Migrating is not justified; invest instead in a wrapper-root + sidecar-config pipeline on top of UnityGLTF.

### Cited Findings

### Inferences

- Sidecar config application pattern (both libraries return a root `GameObject`): (1) instantiate under a disabled wrapper root; (2) compute combined renderer bounds; (3) derive pivot from config (`pivot: "bottom-center" | "center" | explicit offset`) and shift the imported root inside the wrapper so the wrapper's origin is the pivot; (4) apply `scale` as a wrapper-local scale (glTF units are meters; config `realWorldSizeMeters` → uniform scale = target / bounds.size along the config's major axis); (5) store `attachmentType` (plane / face:region / hand:joint / foot / body:joint) and an optional per-attachment offset pose; (6) parent the wrapper under the trackable's anchor transform with the offset. ## Key Question 4 — Attaching to trackables robustly (face, body, hand landmarks → world pose, anchors, smoothing)

### Takeaway
Face attachment should be driven by `ARFace` mesh vertex indices (common to both providers for the mesh, but with different topologies: ARKit ~1220, ARCore 468) plus ARKit-only eye transforms, body attachment by `ARHumanBody.joints` (ARKit only), and 2D ML landmarks should be lifted to world space by casting the camera ray through the landmark and intersecting it with the environment-depth texture (ARCore depth / ARKit LiDAR or human depth), then stabilized with a One Euro filter and anchored via `ARAnchorManager` when the item is world-placed.

### Cited Findings
- `ARFace.updated` "Invoked when the face is updated. If face meshes are supported, there will be updated vertices, normals, indices, and uvs"; `ARFaceMeshVisualizer` renders them. — [AR Foundation ARFace doc](https://raw.githubusercontent.com/needle-mirror/com.unity.xr.arfoundation/master/Documentation~/features/face-tracking/arface.md)
- Eye tracking and blend shapes: ARKit ✓, ARCore –; mesh normals ARCore ✓, ARKit –. — [face-tracking platform-support.md](https://raw.githubusercontent.com/needle-mirror/com.unity.xr.arfoundation/master/Documentation~/features/face-tracking/platform-support.md)
- ARKit face coordinate system: units are meters, origin "centered behind the face", right-handed, +z toward the viewer; `leftEyeTransform`, `rightEyeTransform`, `lookAtPoint` available. — [Apple ARFaceAnchor](https://developer.apple.com/documentation/arkit/arfaceanchor.md)
- ARCore face regions: nose tip, forehead left, forehead right via `ARCoreFaceSubsystem.GetRegionPoses()`. — [ARCore face-tracking.md](https://raw.githubusercontent.com/needle-mirror/com.unity.xr.arcore/master/Documentation~/features/face-tracking.md)
- ARKit 6.3.0 added `XRFaceSubsystem.TryGetBlendShapes` and `XRFaceBlendShapeExtensions`; `ARKitBlendShapeCoefficient` obsolete. — [ARKit CHANGELOG](https://raw.githubusercontent.com/needle-mirror/com.unity.xr.arkit/master/CHANGELOG.md)
- ARHumanBodyManager exposes Pose 2D / Pose 3D / Pose 3D Scale Estimation and a Human Body Prefab. — [body-tracking.md](https://raw.githubusercontent.com/needle-mirror/com.unity.xr.arfoundation/master/Documentation~/features/body-tracking.md)
- Developer observation on iOS 26 regression: expected "~89 joints" per frame from `body.skeleton`, got 0. — [Apple forum thread 804899](https://developer.apple.com/forums/thread/804899)
- ARKit body tracking can run plane detection and image detection concurrently; `automaticSkeletonScaleEstimationEnabled` estimates body height. — [Apple ARBodyTrackingConfiguration](https://developer.apple.com/documentation/arkit/arbodytrackingconfiguration.md)
- Depth textures: ARCore and ARKit both expose raw and smoothed environment depth; "Both raw and smoothed depth are always available if depth is supported, regardless of the value of environmentDepthTemporalSmoothingEnabled". — [ARCore occlusion.md](https://raw.githubusercontent.com/needle-mirror/com.unity.xr.arcore/master/Documentation~/features/occlusion.md); [AROcclusionManager API summary](https://docs.unity3d.com/Packages/com.unity.xr.arfoundation@6.1/api/UnityEngine.XR.ARFoundation.AROcclusionManager.html) (search snippet; page blocked)
- MediaPipe pose world landmarks: "real-world 3D coordinates in meters with the origin at the center between hips". — [mediapipe pose.md](https://github.com/google-ai-edge/mediapipe/blob/master/docs/solutions/pose.md)
- One Euro filter C# for Unity: `unitycoder/OneEuroFilterUnity` ("C# class for Unity rewritten from the original C++ implementation by Nicolas Roussel", supports float/Vector2/Vector3/Quaternion, single .cs, no dependencies); Meta Interaction SDK also ships `OneEuroFilter`. — [OneEuroFilterUnity](https://github.com/unitycoder/oneeurofilterunity); [Meta Interaction SDK reference](https://developers.meta.com/horizon/reference/unity/v71/class_oculus_interaction_input_one_euro_filter)
- AR Foundation 6.6.0-pre.2 added "Dynamic anchor attachment support via `supportsTrackableAttachmentsDelegate`"; 6.2.0 ARCore added Persistent Anchors. — [AR Foundation CHANGELOG](https://raw.githubusercontent.com/needle-mirror/com.unity.xr.arfoundation/master/CHANGELOG.md); [ARCore CHANGELOG](https://raw.githubusercontent.com/needle-mirror/com.unity.xr.arcore/master/CHANGELOG.md)

### Inferences
- Because ARKit and ARCore face meshes have different topologies, define per-platform landmark index tables (e.g., ear-lobe, nose bridge, temple, chin, neck-base extrapolation) and resolve attachment points as weighted averages of a few vertices in `ARFace` space; expose them as named empty transforms on the face prefab (the project already parents jewelry to empties, so only the index resolution needs to become data-driven per provider).
- For glasses, use ARKit eye transforms when available and fall back to nose-tip/forehead region poses on ARCore; for earrings and necklaces, add a gravity-aligned pendulum/physics joint under the anchor so motion looks plausible even with mesh jitter.
- Hand → world: with a 2D landmark (u,v) from BlazeHand/Vision, sample the smoothed environment-depth texture at (u,v) (handle the depth image's different aspect/orientation via `AROcclusionManager`'s display matrix), unproject with the AR camera intrinsics, and derive a ring pose from the proximal-phalanx direction (MCP→PIP vector) and the palm normal (cross of index-MCP→pinky-MCP and wrist→middle-MCP). On ARKit LiDAR devices use environment depth; on non-LiDAR iPhones use human-segmentation depth (A12+) when available; on ARCore use depth where supported, else rely on MediaPipe world landmarks scaled by a hand-size prior.
- Feet: from pose landmarks (ankle, heel, foot-index) build a foot frame; depth-sample at the ankle; place the shoe pivot (config: heel/bottom-center) on the ray-depth intersection; smooth with One Euro (min cutoff ~1 Hz, beta ~0.01–0.05 for 30 fps landmark streams — tuning values are inference, not sourced).
- World-placed products (plane placement) should be re-parented to an `ARAnchor` (via `ARAnchorManager`) after placement so drift correction applies; attach-to-trackable anchoring improved in 6.6.

### Gaps
- The ARKit joint index table (ARHumanBody.joints order / ARSkeleton joint names) was not retrievable this session; the project's existing `BoneController` presumably encodes it and should be treated as the reference until docs can be fetched.
- No primary source quantifying ARKit vs ARCore face-pose jitter or landmark accuracy was found.
- Whether ARCore depth is available during a front-camera face session (needed for necklace/earring depth) is not documented in the fetched pages; ARKit front-camera sessions do not provide scene depth (inference from the face/occlusion docs; not verified).

## Key Question 5 — Occlusion & rendering realism on mobile

### Takeaway
Use `AROcclusionManager` with environment depth + temporal smoothing on both platforms and add ARKit human stencil/depth for hands/feet/body cases on iOS (ARCore has no human segmentation); drive a URP directional light and ambient from AR Foundation light estimation, and use a transparent shadow-receiver plane for grounded shoes/world items. Hard per-tracking-mode triangle/texture budgets were not found in primary sources and must be set empirically.

- WANNA (commercial VTO vendor) notes that "High polygon count models… can't maintain high frame rates on mobile" and high-res (8096²) textures produce files that "may take more than a minute to download". — [WANNA modeling guidelines](https://wanna.helpjuice.com/introduction-modeling) (vendor, no numbers in snippet)

### Inferences
- Occlusion policy per mode: plane placement → environment depth (smoothed); face try-on → no depth occlusion on ARCore; on ARKit the front camera gives no scene depth, so rely on the face mesh as an invisible occluder (Apple documents the face geometry for occlusion); hands/feet/body → ARKit human depth (A12+) + environment depth on LiDAR; ARCore → environment depth only (hand-over-ring occlusion will be weaker on Android; consider a mesh-based hand occluder driven by landmarks).
- Lighting: feed `ARLightEstimationData` into the URP main directional light (color/intensity/direction) and `RenderSettings.ambientProbe` from spherical harmonics on ARKit; ARCore front-camera sessions typically expose only ambient intensity (not verified).
- An "ARShadowReceiver" component does not exist in AR Foundation docs or samples found; implement a URP transparent shadow-receiver shader (shadow-only, alpha = shadow attenuation) on a plane under world/foot items.
- Budgets (inference, to be validated on device): keep try-on items ≤ 50k–100k triangles for face/hand (front camera 60 fps target leaves ~16 ms incl. ML), ≤ 150k for world/body at 30 fps; ≤ 2 materials, ≤ 2048² KTX2 textures; skinned garments ≤ 1 skinned renderer with ≤ 100 bones.

- No primary Unity doc with numeric mobile triangle/texture budgets for AR try-on was found.
- The AR Occlusion Manager and AR Shader Occlusion component sub-pages returned 404 at the guessed mirror paths; details of the URP "AR Shader Occlusion" setup (render feature/keywords) were not captured.
- Light estimation page path not found in the mirror; front-camera light-estimation support per provider unverified.

## Key Question 6 — Automated testing

### Takeaway

## Key Question 7 — Packaging and delivery (Addressables vs raw GLB from CDN, caching, compression)

### Takeaway
For AI-generated per-product GLBs, deliver raw `.glb` (Draco + KTX2) with a JSON sidecar from Firebase Storage/CDN and cache on disk, keeping Addressables only for app-owned content (shaders, face/hand prefabs, filters); Unity's own guidance frames glTF as the choice for "flexible loading of native 3D data… cross platform" and Addressables for Unity-authored DLC/live-service content. No primary cold-load benchmarks for 5–20 MB GLBs were found.

### Cited Findings
- Unity guidance: Addressables is "a high-level system built on top of AssetBundles" recommended for memory management, "DLC packs… delivered over the air", live-service updates; glTF recommended for "pure 3D content… flexible loading of native 3D data and… cross platform compatibility"; Addressables handles cache vs remote CDN automatically. — [Unity: Choosing the right runtime asset loading technology](https://unity.com/resources/runtime-asset-loading-technology-for-rt3d); [Unity blog: 3 runtime asset loading options compared](https://unity.com/blog/comparing-runtime-asset-loading-technology) (search snippets; pages blocked)
- UnityGLTF supports Draco, KTX2 (basisu) and meshopt via Unity's `com.unity.cloud.draco`, `com.unity.cloud.ktx`, `com.unity.meshopt.decompress` packages; runtime loading from web URLs via `UnityWebRequestLoader`. — [KhronosGroup/UnityGLTF](https://github.com/KhronosGroup/UnityGLTF)
- glTFast requires KTX for Unity ≥ 3.6.0 and Draco for Unity ≥ 5.4.0; added "Android JAR URI handling improved" and visionOS compatibility. — [glTFast CHANGELOG](https://raw.githubusercontent.com/needle-mirror/com.unity.cloud.gltfast/master/CHANGELOG.md)
- KTX2/Basis: single file transcodes "to whatever format the user's GPU prefers, such as ASTC on iOS and ETC2 on Android"; stays compressed into VRAM, "typically cuts texture memory 4× to 8×". — [Khronos KTX2 link page](https://www.khronos.org/developers/linkto/compressed-texture-transmission-ktx2-basis-universal); [Basis Universal explainer](https://svilenkovic.com/3d/basis-universal) (secondary)
- UnityGLTF 2.19.2 reduced memory usage during texture importing; 2.18.8 added mesh dedup with Jobs and reduced import memory footprint. — [UnityGLTF releases](https://github.com/KhronosGroup/UnityGLTF/releases)
- BlazePose model sizes (lite 10.6 MB / full 14 MB / heavy 34.9 MB) and ML Kit pose SDK size (~10–13 MB) indicate ML model payloads comparable to a product GLB. — [TensorFlow blog](https://blog.tensorflow.org/2021/05/high-fidelity-pose-tracking-with-mediapipe-blazepose-and-tfjs.html); [ML Kit pose](https://developers.google.com/ml-kit/vision/pose-detection) (search snippet)

### Inferences
- Pipeline: asset service emits `{sku}.glb` (Draco geometry, KTX2/UASTC or ETC1S textures, ≤ 2048²) + `{sku}.config.json` (pivot, scale, attachment, rig, version hash) → Firebase Storage behind CDN with immutable, content-hashed paths → client downloads with `UnityWebRequest`, stores in `Application.persistentDataPath` keyed by hash, loads via UnityGLTF `GLTFSceneImporter` async off the main thread where supported, instantiates under the wrapper root.
- Ship ML models (BlazeHand/BlazePose ONNX) inside the app (StreamingAssets or Addressables local) rather than per-product; keep AR-mode scenes/prefabs in Addressables for OTA fixes without store review.
- Expect Draco decode + KTX2 transcode to dominate cold-load for 5–20 MB GLBs on mid-range phones; measure with Unity Profiler markers around import stages; pre-warm shader variants (URP Lit with needed keywords) to avoid first-use hitches.

### Gaps
- No primary measurements of cold-load time for 5–20 MB GLBs on iOS/Android with UnityGLTF or glTFast were found.
- Firebase Storage/CDN size limits and caching headers were not researched (out of the Unity-side scope; no sources fetched).
- Platform-specific KTX for Unity transcode-format matrix (which ASTC block sizes on iOS vs ETC2 on Android) not retrieved (README lacked it).
